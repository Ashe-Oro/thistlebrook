# Registry lane: eighteen districts

Local continuation of `sol-registry` on the integrated 18-district world. No licensed models or textures are included. Development and browser verification use **5199** with strict port selection.

## Result and coverage

At seed 831, **670/670 placed model instances** and **1,419/1,419 logical placements** have registry records. There are 1,575 total records, including destinations, infrastructure, furniture and independently reservable activities. All 561 owned GLBs and 86 alternate-format aliases retain their measured catalog metadata. Scenery uses 81 distinct owned models; **386 of 467 individual assets remain unused**, plus 94 authoring/prebuilt/whole-pack reference records. The full list is [REGISTRY-UNUSED-ASSETS.md](REGISTRY-UNUSED-ASSETS.md); per-district counts and the exact seed inventory are [REGISTRY-INVENTORY.md](REGISTRY-INVENTORY.md).

The browser independently confirms **410/410 expansion model instances** at seed 831, 401/401 at seed 0 and 404/404 at seed 99, with no missing rendered identities. Counts vary with woodland scatter. Model instances are distinct from their mesh pieces; procedural architecture/effects inherit a named assembly, and generated character rigs are actors rather than scenery utilization.

## Compiler and renderer contract

- `registry/district-models.json` is a reviewable placement manifest for 250 static expansion models. It stores identity, asset/path, transform, measured size and elevation, with an ordinal for the seven animated fair ducks. No geometry bytes are stored. `model-id.js` derives IDs from the district, asset and transform, independent of asynchronous load order.
- `registry/seed-models.js` provides seed-specific woodland trees and four fallen logs. Logs have their own deterministic random stream, so water effect randomization cannot change placement identity. These 160 seed-831 records are generated by the compiler, not copied from the reference manifest.
- `tagDistrictModels` verifies each owned model against its compiled ID before static batching. Every batcher preserves the source ID alongside each instance matrix. `buildInFrame` and `tagAssembly` fill assembly ownership only for components without an individual identity. The coverage audit detects registered expansion models/furniture that disappear from the rendered scene as well as unknown mesh/instance IDs.
- `expansion-placements.js` joins model placements to canonical owned metadata: size, semantic type, scene families, animation information and local interaction templates. Model affordances are transformed back through source coordinates into placement space. New benches retain disabled measured candidate seat poses until a verified approach is supplied; vehicle templates remain local until boarding anchors are authored. The older street-bench adapter also uses these measured seat positions/heights instead of its previous guessed height. Decorative equipment has an explicit disabled reason and no pedestrian node.
- `district-furniture.js` inventories 28 Coral Coast dining tables, 19 umbrellas, three fair picnic tables and six Pinecrest picnic tables. Table components and coast diners carry the corresponding furniture ID through instancing. Rooftop seats retain elevation and their `coast-stairs` navigation domain; they are not flattened into executable global seat routes.

Static renderer transforms remain authored in their district modules. Changing one without regenerating/reviewing its manifest fails explicitly at load time. This makes drift visible while preserving the districts' existing local drawing code. New rest scenes are fully compiler-authored. Other procedural subparts remain components of their named venue or district assembly; this is a logical prop registry, not a mesh-by-mesh object database.

## Small prop scenes and spacing

`scenes.json` adds nine selectable public-stop families and explicit recipes. Recipe membership is included by `assetGroups`/`groupAssets`, so the atlas and procedural group compiler can select these families without rewriting measured geometry records.

Every new district gets a three-member scene: a measured log bench, context supplies, and a small detail. Harbor uses a crate and lantern; fair a basket and mums; outskirts a food locker and lantern; airport a plant and crate; skatepark a barrel and plant; Pinecrest a sign and basket; coast bonsai and a stone lantern; Roadster a crate and barrel; Starbase a plant and lantern. The town now has **19 catalog scenes, 55 member props and 23 catalog activity slots**.

`compileExpansionScenes` chooses a deterministic public-road candidate using measured model envelopes, venue/ride reservations, existing furniture and other scene pads. It reserves 0.6m and 0.5m companion edge gaps, a 0.9m front aisle and 0.38m actor clearance. Existing fire, table/seat and other pair rules still apply. Candidates must remain on supported town/region land; lake margins and harbor water are excluded. Member footprints clear roads, and the public connector clears obstacles. Roads and slot approaches are inserted into the shared graph before registry construction. Fair and Switchyard forecourts and the Roadster east viewing apron have explicit supporting region bounds; the Roadster apron has ground geometry.

These are measured AABB rules, not a free-space navigation mesh. Assembly-owned local paths and elevated circulation remain under their district controller.

## Activities and public access

The nine new catalog seats use the existing resident executor's exclusive leases and seat animation. Afternoon schedules already choose eligible seats, and passing residents can take a rest along an actual route. There is no dialogue system.

Fair's 29 authored visitor slots now have canonical activity, animation, capacity, hours and approach metadata. `district-activities.js` supplies the same slot positions and local paths to the fair controller and the global query facade. `interaction.controller: 'fair'` keeps those leases out of the town resident executor; ordinary residents can still visit venue entrances. This avoids two schedulers occupying the same physical slot. Coast's dining poses and stair paths retain their local controller and candidate metadata.

`findPlace` accepts exact IDs, case-insensitive names, straight/curly apostrophes and authored aliases. Every selectable named attraction and all 30 navigation destinations/labels resolve through `walkTo`. New Starbase names include Megabay, High Bay, Starfactory, Starship/Mechazilla, tank farm, Falcon pad, both landing zones and the drone ship. Their `accessPolicy: 'public-viewpoint'` routes to the **Starbase Visitor Garden**. Equipment coordinates remain inspectable; a route never crosses the launch range to reach a model centre. Closed venues and unverified decorative props continue to fail access checks explicitly.

## Reproduce

```sh
npm run dev -- --port 5199 --strictPort
npm run capture:astra:registry -- --write
npm run inventory:astra:registry -- --write-doc
npm run test:astra:registry:expansions
npm run test:astra:registry:browser
node --test --test-concurrency=3 tests/astra*.test.mjs tests/sunbeam.test.mjs tests/skatepark.test.mjs
npm run build
```

Capture uses `?registryCapture` to inventory existing district source models before the new scene layout is planned. The capture command removes seed-authored trees/logs and sorts the remaining records before writing the manifest. Normal runtime never registers an unknown model silently. Named attraction envelopes are recorded separately in `district-landmarks.json`; review these when adding or moving selectable architecture. Inventory regeneration also writes ignored JSON under `out/astra/` and the tracked unused asset report.
